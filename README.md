# rustdesk-server-setup

Установка и обслуживание собственного сервера RustDesk (бесплатная версия
`rustdesk/rustdesk-server`, контейнеры `hbbs` и `hbbr`) на Debian и Ubuntu
одной командой `rustdesk-ctl`.

Что получается после установки:

- `hbbs` (ID-сервер) и `hbbr` (ретранслятор) в Docker с сетью хоста, образ
  закреплён по digest;
- запуск через systemd: `rustdesk-compose.service`;
- еженедельное обновление образа с проверкой и откатом:
  `rustdesk-update.timer`;
- watchdog, который поднимает упавший сервер: `rustdesk-watchdog.timer`;
- проверка ключа `-k _`: сервером могут пользоваться только клиенты, у
  которых указан его публичный ключ;
- команды для статуса, версии, журналов и смены ключа.

## Требования

- Debian 12/13 или Ubuntu 22.04/24.04/26.04 с systemd, доступ root.
- Docker CE с плагинами `docker-compose-plugin` и `docker-buildx-plugin`.
  Если Docker нет, установщик поставит его сам с ключом `--install-docker`.
- Открытые порты: TCP 21115, 21116, 21117 и UDP 21116.

## Установка

```bash
git clone https://github.com/civisrom/rustdesk-server-setup.git
cd rustdesk-server-setup
sudo ./rustdesk-ctl install
```

Без git:

```bash
curl -fsSL https://github.com/civisrom/rustdesk-server-setup/archive/refs/heads/main.tar.gz | tar -xz
cd rustdesk-server-setup-main
sudo ./rustdesk-ctl install
```

В конце установщик выводит публичный ключ. В клиенте RustDesk откройте
«Настройки → Сеть → ID/Ретранслятор» и укажите:

- **ID-сервер**: адрес вашего сервера;
- **Ретранслятор**: можно оставить пустым, клиент возьмёт адрес ID-сервера;
- **Ключ**: выведенный публичный ключ;
- **Сервер API**: оставьте пустым (см. ниже).

Ключи установки:

| Ключ | Что делает |
|------|------------|
| `--install-docker` | Ставит Docker CE из официального репозитория download.docker.com (ключ репозитория сверяется по SHA256) и отключает управление файрволом в Docker (см. ниже) |
| `--no-auto-update` | Не включать еженедельное обновление |
| `--no-watchdog` | Не включать watchdog |

### Docker без управления файрволом

С `--install-docker` установщик записывает в `/etc/docker/daemon.json`:

```json
{
  "iptables": false,
  "ip6tables": false,
  "userland-proxy": false
}
```

Docker перестаёт создавать свои правила iptables и NAT, и правилами
полностью управляет файрвол хоста (nftables). Существующий `daemon.json`
не заменяется: в него добавляются эти три параметра, а прежний файл
сохраняется рядом как `daemon.json.backup.<время>`. Если Docker не
запускается с новыми настройками, прежний файл возвращается на место.
RustDesk работает в сети хоста, поэтому NAT Docker ему не нужен. Другим
контейнерам в сетях bridge без NAT от Docker нужны собственные правила
nftables.

## Команды

```bash
sudo rustdesk-ctl status        # службы, контейнеры, порты, ключ, watchdog, ошибки в журнале
sudo rustdesk-ctl version       # закреплённый образ, версии hbbs/hbbr, есть ли новый образ
sudo rustdesk-ctl update        # обновить сейчас (с проверкой и откатом)
sudo rustdesk-ctl logs [N]      # последние N строк журналов hbbs и hbbr (по умолчанию 100)
sudo rustdesk-ctl key show      # публичный ключ для клиентов
sudo rustdesk-ctl key rotate    # новая пара ключей
sudo rustdesk-ctl uninstall     # удалить, сохранив пару ключей
```

`status` завершается с кодом 1, если что-то не работает, поэтому его можно
вызывать из своих скриптов мониторинга.

Службы systemd:

```bash
systemctl status rustdesk-compose.service      # сервер
systemctl restart rustdesk-compose.service     # перезапуск hbbs и hbbr
systemctl list-timers 'rustdesk-*'             # когда следующее обновление и проверка
journalctl -u rustdesk-update.service -n 50    # журнал обновлений
journalctl -u rustdesk-watchdog.service        # что делал watchdog
```

## Обновление сервера RustDesk

`rustdesk-update.timer` запускается по воскресеньям в 04:00 по местному
времени со случайной задержкой до часа. Если машина была выключена, проверка
выполнится после загрузки.

Почему раз в неделю. Бесплатный `rustdesk-server` выходит нерегулярно:
1.1.12 — октябрь 2024, 1.1.13 — январь 2025, 1.1.15 — январь 2026,
1.1.16 — июль 2026. Между релизами проходит от двух до двенадцати месяцев,
но исправленные выпуски (`-1`, `-2`) выходят через несколько дней после
основного. Образ в Docker Hub публикуется сразу после релиза. Проверка
сравнивает только digest и почти ничего не стоит, если образ не менялся,
а ежемесячная проверка задержала бы исправления на срок до месяца.

Как проходит обновление:

1. Читается digest тега `latest` в Docker Hub. Если он совпадает с текущим,
   ничего не происходит.
2. Новый digest записывается в `/opt/rustdesk/.env`, образ скачивается,
   контейнеры пересоздаются.
3. Через 15 секунд проверяется, что `hbbs` и `hbbr` работают, слушают
   порты и не перезапускались. У образа нет healthcheck, и
   `docker compose up --wait` считает падающий контейнер здоровым, поэтому
   нужна отдельная проверка.
4. При ошибке возвращается прежний образ и выполняется та же проверка.
   Если и откат не удался, прежние настройки остаются в
   `/opt/rustdesk/.env.backup.*`, а служба завершается с ошибкой.
5. После успешного обновления старый образ удаляется.

## Watchdog

Docker сам перезапускает упавший процесс (`restart: unless-stopped`).
Watchdog закрывает остальные случаи: контейнер остановлен или удалён, порт
перестал слушаться.

- Проверка раз в 3 минуты (`rustdesk-watchdog.timer`, первая — через 5 минут
  после загрузки). Она обращается к `docker inspect` и `ss`, занимает
  доли секунды и запускается с пониженным приоритетом процессора и диска
  (`Nice=10`, `IOSchedulingClass=idle`, `CPUQuota=20%`, `MemoryMax=128M`).
  Удачные проверки в журнал не пишутся.
- Сбой должен держаться 20 секунд, иначе он считается кратковременным.
- Затем выполняется `systemctl restart rustdesk-compose.service`, и через
  15 секунд проверяется результат.
- Не больше 3 перезапусков в час. Дальше watchdog только пишет ошибку в
  журнал и не перезапускает: если сервер падает снова и снова, перезапуск не
  поможет, нужно смотреть `rustdesk-ctl logs`.
- Если вы сами остановили `rustdesk-compose.service`, watchdog ничего не
  делает. Во время обновления или смены ключа проверка пропускается.

## Ключ сервера

`hbbs` и `hbbr` запускаются с `-k _`. Сервер обслуживает только клиентов, у
которых в поле «Ключ» указан его публичный ключ: остальные получают отказ и
на ID-сервере, и на ретрансляторе. Кроме того, `hbbs` подписывает приватным
ключом ключи клиентов, а клиент проверяет подпись. Не заменяйте `-k _` на
`-k <пароль>`: тогда `hbbs` остаётся без приватного ключа и перестаёт
подписывать ключи клиентов.

Публичный ключ не секретный: без пароля или подтверждения на удалённом
компьютере он доступа к компьютерам не даёт. Но если он попал к посторонним,
они могут пользоваться вашим сервером как ретранслятором. Тогда смените ключ:

```bash
sudo rustdesk-ctl key rotate
```

Команда останавливает контейнеры, переносит старую пару в
`/opt/rustdesk/key-backups/<время UTC>/`, даёт `hbbs` создать новую,
запускает оба контейнера и проверяет, что они загрузили новый ключ. При
ошибке или прерывании старая пара возвращается на место. После смены
клиенты со старым ключом не подключатся, пока в них не введут новый.

Вернуть прежнюю пару вручную:

```bash
sudo systemctl stop rustdesk-compose.service
sudo cp /opt/rustdesk/key-backups/<время>/id_ed25519* /opt/rustdesk/data/
sudo systemctl start rustdesk-compose.service
```

Приватный ключ `/opt/rustdesk/data/id_ed25519` хранится в каталоге с
правами 700 и с правами 600 (`hbbs` 1.1.16 создаёт его с 0644).

## Поле «Сервер API» в клиенте

Новые клиенты RustDesk предупреждают: «Если поле „Сервер API“ пустое, ваш
собственный сервер по умолчанию использует HTTP». API на порту 21114 есть
только в платной RustDesk Server Pro. В бесплатном сервере его нет, порт
21114 никто не слушает, поэтому предупреждение можно не замечать. Ключ
сервера в API не передаётся. Не вписывайте в это поле случайный адрес
`https://`: клиент начнёт отправлять туда сведения о системе.

## Файрвол

Нужны TCP 21115–21117 и UDP 21116. Порты 21118 и 21119 (веб-клиент) и
21114 (API Pro) открывать не нужно. Пример для nftables:

```
tcp dport { 21115, 21116, 21117 } accept
udp dport 21116 accept
```

Если клиенты подключаются из известных сетей, ограничьте доступ их
адресами: это защищает ретранслятор даже при утечке публичного ключа.

## Обновление rustdesk-ctl и переход с debian-ubuntu-setup

Обновить сам `rustdesk-ctl`, юниты и compose:

```bash
cd rustdesk-server-setup
git pull
sudo ./rustdesk-ctl install
```

Повторная установка сохраняет пару ключей и текущий образ. Контейнеры
пересоздаются, только если изменилась их конфигурация.

Сервер, установленный опцией RustDesk из
[debian-ubuntu-setup](https://github.com/civisrom/debian-ubuntu-setup),
переводится той же командой `install`. Каталог `/opt/rustdesk`, ключи и
имена служб совпадают, а старый `/usr/local/sbin/rustdesk-safe-update.sh`
удаляется: обновление теперь выполняет `rustdesk-ctl update`.

## Удаление

```bash
sudo rustdesk-ctl uninstall            # удалить всё, кроме пары ключей в /opt/rustdesk/data
sudo rustdesk-ctl uninstall --purge    # полное удаление, включая ключи
```

Без терминала команда требует `--yes`. Удаляется всё, что относится к
RustDesk:

- службы и таймеры `rustdesk-*` (сначала отключаются и останавливаются),
  их drop-in-каталоги `*.service.d`, ссылки в `*.wants` и файлы таймеров в
  `/var/lib/systemd/timers`;
- контейнеры `hbbs` и `hbbr` (и любые другие контейнеры проекта Compose
  `rustdesk`);
- все образы `rustdesk/rustdesk-server`, в том числе старых версий;
- `/usr/local/sbin/rustdesk-ctl`;
- остатки версии из debian-ubuntu-setup: `/usr/local/sbin/rustdesk-safe-update.sh`
  и `/run/lock/rustdesk-update.lock`;
- содержимое `/opt/rustdesk`, кроме `data/` и `key-backups/`, а с
  `--purge` — весь каталог.

Повторная установка после обычного удаления подхватывает сохранённую пару
ключей, и клиенты продолжают работать без изменений. Повторный запуск
удаления на чистой системе безопасен.

Не удаляются: Docker (он может быть нужен другим программам), его
`/etc/docker/daemon.json`, записи RustDesk в журнале systemd (они
удалятся по обычной ротации журнала) и каталог, куда вы клонировали этот
репозиторий. Если Docker нужен был только для RustDesk, удалите его
отдельно: `sudo apt purge docker-ce docker-ce-cli containerd.io
docker-buildx-plugin docker-compose-plugin`.

## Файлы

| Путь | Назначение |
|------|------------|
| `/opt/rustdesk/docker-compose.yml` | Конфигурация контейнеров |
| `/opt/rustdesk/.env` | Текущий образ (пишет `rustdesk-ctl update`) |
| `/opt/rustdesk/data/` | Ключи и база `hbbs` (права 700) |
| `/opt/rustdesk/key-backups/` | Прежние пары ключей после `key rotate` |
| `/opt/rustdesk/.update.lock` | Блокировка обновления, смены ключа и watchdog |
| `/opt/rustdesk/.watchdog-restarts` | Время перезапусков watchdog за последний час |
| `/usr/local/sbin/rustdesk-ctl` | Команда управления |
| `/etc/systemd/system/rustdesk-*` | Службы и таймеры |

## Что ещё стоит знать

- Раз в сутки `hbbs` сам запрашивает `https://api.rustdesk.com/version/latest`
  и отправляет туда ОС, её версию, архитектуру и отпечаток устройства. Так
  устроена бесплатная версия; ключи туда не передаются. Если это
  нежелательно, запретите серверу исходящие соединения к этому адресу.
- Контейнеры работают с `cap_drop: ALL` и `no-new-privileges`.

## Разработка и тесты

```bash
shellcheck rustdesk-ctl tests/e2e.sh
python3 tests/test_rustdesk_ctl.py           # модульные тесты с имитацией docker/systemctl
RUSTDESK_E2E=1 sudo bash tests/e2e.sh        # полный прогон на одноразовой машине
```

`tests/e2e.sh` устанавливает RustDesk в `/opt/rustdesk` и проверяет
установку, повторную установку, смену ключа, обновление через systemd,
откат неудачного обновления, watchdog и его ограничение, взаимную блокировку
обновления и смены ключа, прерывание смены ключа, удаление с повторной
установкой и полное удаление с поиском остатков по всей файловой системе.
Запускайте его только на тестовой машине.
